# Software Factory

A pipeline that takes items from `BACKLOG.md` through Triage → Spec → Build → Check → Review,
with a control-plane GUI to follow. This file is the single rules file for every agent and
model working here; `CLAUDE.md` only imports it.

## Commands

- `bun test` and `bun run typecheck` — the gate. Both must pass before any stage is done.
- `bun run e2e` — browser end-to-end test of the GUI with dry runs. Needs Chrome; not part of the gate.
- `bun run smoke` — opens every view at desktop and phone width on a project seeded with every state; fails on a console error or an accessibility violation (axe). Needs Chrome; not part of the gate. Run it after any GUI change, and add what you build to it.
- `bun run site` — opens the landing page and the documentation (`site/`) at desktop and phone width, scrolls through the page with and without reduced motion, follows every link, and fails on a console error or an accessibility violation (axe). Needs Chrome; not part of the gate.
- `bun run evals:roles [--model haiku] [--case <id>] [--runs N] [--dry-run]` — behaviour evals for the roles (`evals/roles/cases.ts`): one real model stage per case, on a throwaway project made from today's catalog, under pressure to skip a step, graded by the factory's own rules. Spends tokens (a few cents on Haiku); not part of the gate. After changing a role's instruction, run it; when you add a case, give it a good and a bad script (`bun test` checks its grader tells them apart).
- `bun run evals:plugin [claude plugin eval options]` — does a natural request reach the right slash command, and does a casual one never reach one only the person may give (`evals/plugin/`, run with `claude plugin eval` on a temporary copy of the plugin, with and without it). Spends tokens (a few cents on Haiku, one run per case); not part of the gate. Run it after changing a skill's description. The judge reads the whole trace (`focus: trace`); the shell is off in its sandbox, so a case judges the route taken, not the command's result.
- `bun run rehearse <project folder>` — this version tried on a private clone of a real factory project before a release (F-101): the commands a person runs, the dashboard started as `/software-factory:open` starts it, and every page's data; then what an update would change. No model, no GitHub, the project untouched. Part of the release checklist in `docs/PLUGIN.md`.
- `bun run factory run [F-id...] [--parallel N] [--stub] [--anyway]` — run the top Ready item(s) that are not waiting for another task to land, or the named ones (a task with `Depends on:` is refused until what it needs is merged into main; `--anyway` is the person's word to build it without), each in its own worktree. `--stub` makes no model calls.
- `bun run factory update <F-id>` brings a waiting task up to date with main (a merge into its own branch; the Builder resolves a clash). `bun run factory approve <F-id>` / `reject <F-id> --feedback "…" [--files a,b]` / `discard <F-id>` — a person accepts a finished task, sends it back to the Builder with comments (same branch, same spec, a new round), or throws it away. With a GitHub `origin`, approving keeps the branch and pushes nothing.
- `bun run factory push <F-id>` (or `push <F-id> <F-id>... --together`: one pull request for several tasks) / `merge <F-id>` (or `merge batch-<time>`) / `revert <F-id>` / `sync` / `vcs [auto-merge on|off | auto-push on|off | ci | fix <F-id>]` — GitHub, only on request: push an approved task and open its pull request (secret scan first), merge it (refuses failing checks), update from GitHub, show what is waiting. Auto-merge is off unless a person turns it on, and needs a workflow to wait for.
- `bun run factory authority` — who may do what in this project, and whether the rules about it hold (`plugin/engine/authority.ts`: exit 1 when one is broken). Before adding a capability to a role, a skill, a conversation or a script, read the rules at the top of that file: the checks refuse what contradicts them, and `tests/factory.test.ts` ("authority") searches every move of every responsibility.
- `bun run factory manager [autopilot|assist|off | report | set <setting> <value>]` — what the Technical Manager may do by itself (autopilot is the default: it starts what you ask it to build, recovers a stuck task, and stays inside the spend and retry limits; `report` prints the facts behind her milestone, retrospective and team-health answers, from `plugin/engine/retro.ts`). `factory consult <topic> "<question>"` asks one role a question, read-only.
- `bun run factory deliver` — autopilot only (F-124, `plugin/engine/deliver.ts`): one step of carrying approved tasks to GitHub, by code, never a model: push the next approved task in integrate order and open its pull request, or merge the one open pull request when its checks pass. The dashboard runs it every minute on autopilot.
- `bun run factory rebuild <F-id>` — the way out of a clash too large to update: closes the task's open pull request, drops its branch, moves it to Ready; run it again to build on today's main. The Rebuild it button on a conflicting pull request does both.
- `bun run factory serve [port]` — local control plane on `127.0.0.1`, one port per project in 4400-4499 (from its path; `serve` moves to the next free one, and reports if this project's is already up): the GUI (overview, backlog, talk, team, agents, logs, worktrees, studio, graph), a live event stream, and the endpoints behind them. Studio saves commit the edited file, with a message the person can edit.
- `bun run factory add "<title>"` — add an item to Inbox.
- `bun run factory skill add <owner/repo@skill> --role <role>[,<role>...]` — install a skill for one or several roles. `skill attach|detach <skill> --role <role>[,<role>...]` for one already installed. Each is committed, because task worktrees branch from HEAD.

## Layout

- `plugin/` — **the product**, and the only folder users receive. Read `docs/PLUGIN.md` before changing its layout, adding a dependency or releasing.
- `plugin/engine/` — orchestrator: `config`, `events` (SQLite log), `backlog`, `pipeline`, `claude` (headless runner), `worktree`, `hooks` (guard and gate), `server`, `skills`, `cli`.
- `gui/` — source of the control plane page (React, plain CSS): `data.ts` holds the hooks (event stream, polled backlog, theme), `app.tsx` the shell and Overview, `backlog.tsx` the Backlog (the board with its cards, and the side panel for one task: pipeline stepper, Summary, Activity with replay, Spec, Review and the changes), `views.tsx` the Agents, Logs and Worktrees views, `studio.tsx` the Studio (files, editor with changed-line marks, Preview, History, and saving in two checks; its line differences come from `linediff.ts`), `team.tsx` the Team view, `manager.tsx` the Technical Manager's strip on Overview and her settings in Team (data from `/api/manager` and the `manager.*` events), `talk.tsx` the Talk and Checks views (the message box grows with its text, files attach by button, drop or paste, a message sent while a reply is coming waits its turn, and what a reply ran is a folded, expandable step list), `chatstore.ts` brings the conversations the server keeps into the page (and hands over, once, what an earlier version kept in the browser), `mdparse.ts` and `markdown.tsx` the Markdown a reply is written in (a tree, never HTML; no dependency), `vcs.tsx` the GitHub tile and rail chip, `source.tsx` the Source view (Changes and Log tabs; data from `plugin/engine/source.ts`), `diff.tsx` the file tree, `+/−` stats and unified diff, `commitgraph.tsx` the lane graph, `palette.tsx` the command palette (⌘K: the factory's own checks, go-to, actions, Ask Bix), `health.tsx` the Health strip and rail chip (data from `plugin/engine/health.ts`: quick free checks, no model), `person.tsx` one person's panel (live feed, files touched, recent stages; opens from any robot), `live.tsx` what each agent is doing now (the "Now" line and recent actions from the tool events, the tab title and icon, opt-in desktop notifications; the wording comes from `doing` and `liveOf` in `plugin/engine/state.ts`), `icons.tsx` the inline icons, `robots.tsx` the twelve robot avatars (one per role; `personaFor` gives a role its robot and name, a made-up role gets one by its name), `ui.tsx` the dropdown that replaces the browser's menu (`Select`, in a portal, keyboard-driven) and the skeleton placeholders. Do not use a native `<select>`. It is built into `plugin/dist/`, which is committed. `plugin/engine/state.ts` folds the event log into what the page and `factory status` show.
- `plugin/skills/` — the slash commands (`/software-factory:init`, `git`, `add`, `run`, `status`, `open`, `approve`, `discard`, `doctor`, `manage`). Each is a thin wrapper over `factory`; put logic in the engine.
- `plugin/templates/catalog.json`, `presets.json` — the responsibility catalog and the team presets (see `docs/ROLES.md`); `plugin/engine/chronicle.ts` parses the Scribe's reply and appends the chronicle and role notes when a task is approved; `plugin/engine/graph.ts` runs graphify. `plugin/engine/teamctl.ts` changes a project's team (checked against the rules, config and role files updated together). `plugin/engine/vcs.ts` is the deterministic side of git and GitHub (status, push, pull request, merge, sync); the Release Engineer holds it (G1 setup, G2 what is waiting). It talks to GitHub only through `gh` (`FACTORY_GH` overrides it in tests), never pushes or merges unprompted, and the GUI chat can only propose a push (a `PROPOSE:` line the page turns into a button). `plugin/engine/release.ts` is the deterministic side of releasing (version files, readiness checks, the commit-and-tag step); it never pushes or deploys. `plugin/engine/estimate.ts` estimates what a task costs for a team (observed stage costs, else a per-model guide); `plugin/engine/chat.ts` runs the GUI's conversations (documents only, no deploy; the Guide topic is read-only, with its own prompt and its own short allow-list, and has no responsibility behind it); `plugin/engine/chatlog.ts` keeps each conversation on disk in the project (`.factory/chats/<topic>.json`, text only, capped, never committed): the server writes every turn before it answers, and the page shows what the server holds (a compaction runs Claude's own `/compact` on the session and leaves a divider message); `plugin/engine/commands.ts` builds what the message box offers when a slash is typed (the dashboard's own `/compact` and `/clear`, the project's skills and commands, and plugin commands, taken from what the conversation's agent reports: no list per kind of agent, and a runner for another agent only hands over the names its session reports); `teamctl.ts` also builds the Team view data and previews a change (`planTeam`) without writing. `plugin/engine/security.ts` is the deterministic security gate: change-set parsing, the secret scan and the sensitive-area triggers. `plugin/engine/team.ts` validates a team and assembles role files (unattended roles) and chat prompts (`factory role`, used by the brainstorm, research and plan skills) from it. A project's team is a preset in `presets.json` plus its own changes under `team` in the config (`resolveTeam`); pipeline stages find their role by who holds the stage's responsibility. Skills name responsibilities (`factory role D1 D3`), never roles. A catalog entry's `how` decides which: `chat` runs in the user's session, `headless` is an agent stage. Add a responsibility's `instruction` to the catalog to make it real.
- `plugin/templates/` — rules and backlog that init writes into a project (role files and config come from the catalog). `plugin/bin/factory` is the executable.
- `site/` — the landing page (plain HTML, CSS and one script, no build): scroll motion is an observer for reveals and one handler for the pinned "how it works" section; `img/hero.jpg` is a real dashboard screenshot (`video/capture-stills.ts` takes them). `docs/` is built from `plugin/README.md` and `plugin/docs/RUNBOOK.md` by `bun site/build-docs.ts` and committed: edit the Markdown, rebuild, commit both. Dev side, not part of the plugin.
- `tests/` — unit and HTTP tests. `e2e/` — the browser test. `tests/fixture.ts` builds the throwaway repo both test suites use.
- `.worktrees/<F-id>/` — one git worktree and `factory/<F-id>` branch per task. Not committed.
- `factory.config.json` — model, effort and fallback chain per role. It owns model choice; agent files do not set `model`.
- `.claude/agents/<role>.md` — role prompt, tools and skills. Each stage runs as `claude -p --agent <role>` with project settings only; only the builder may change files.
- `.factory/` — run artifacts and `events.db`. Not committed.
- `graphify-out/` — knowledge graph of this repo.

## Rules

1. **Graph first.** Read `graphify-out/GRAPH_REPORT.md` or run `graphify query "<question>"` before opening source files.
2. **Files are the handoff.** Each run has a directory under `.factory/runs/` holding `task.md`, `triage.md` (only for ad-hoc items), `spec.md`, `build.md`, `review.md`. Read what earlier stages wrote; do not assume shared memory with another model. Your final reply is your stage's output: the orchestrator saves it, so do not write into `.factory/` yourself.
3. **Never edit governance files:** `BACKLOG.md`, `factory.config.json`, `AGENTS.md`, `CLAUDE.md`, `.claude/`, `.git`, `.factory/`, `graphify-out/`. A guard hook blocks it. Never commit, push or open pull requests; the orchestrator does that after a person approves. If you find work outside your task, end your output with a `## Follow-ups` heading and one `- ` line per item; it goes to Inbox for a person to promote.
4. **Stay in scope.** Do the task in `task.md` and nothing else.
5. **Least code that works.** Reuse what is in this repo, then the standard library, then the platform, then an installed dependency. No new dependency for what a few lines do. No abstractions, config or scaffolding for needs that do not exist yet.
6. **Never cut:** input validation at trust boundaries, error handling that prevents data loss, security checks, tests for non-trivial logic.
7. **No secrets in files.** Config holds environment variable names, never key values.
8. **Product and development stay apart.** Anything the product needs at runtime lives in `plugin/`; tests, dev skills and this repo's own backlog, config and role files never go there. The factory is not used to develop itself.
9. **Bun only.** Use `bun`, `bun test` and `bun:sqlite`; do not add Node-only tooling.
10. **Version control looks like GitHub and VS Code.** Anything about git or GitHub in the dashboard follows their layouts, icons, state colours (open green, merged purple, closed red), M/A/D/U letters and the green merge button, so it is familiar to people who use them. Do not invent a new design for it.
